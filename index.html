동시성 · 성능선착순 재고 경합 구조 개선 — 단일 카운터 도입▶
문제
예약 오픈 시 높은 트래픽에서 재고를 정확히 차감하면서 성능도 유지해야 했습니다. 기존 DB 원자적 업데이트는 정합성은 보장되나 row lock 경합으로 응답 대기 시 병목이 생겼습니다.
원인
같은 슬롯에 요청이 몰리면 DB row lock을 두고 경합이 발생하고, 대기가 쌓이며 처리량이 떨어집니다.
해결 과정
  1. Redis 원자 연산으로 옮겨 경합 구간을 짧게 만들어 처리량과 응답시간을 개선하고자 했습니다.
  2. Redis 선차감으로 옮기자 GET-DECR 사이에 다른 요청이 끼어들어 과예약이 발생했습니다.
  3. Lua Script와 단일 카운터를 검토했습니다. 둘 다 과예약은 없었으나 Lua는 단일 스레드 특성상 성능이 저하됐습니다.
  4. GET 없이 DECR 한 번으로 차감하고 음수면 INCR로 롤백하는 단일 카운터 방식을 택했습니다.
결과
DB 락 방식 대비 TPS 1.9배 · p95 7.8배, Lua 대비 p95 5.1배 개선. 정확성은 단위 테스트로 검증했습니다 — DECR 음수 시 롤백과 DB 저장 차단, 저장 실패 시 복구가 동작합니다.
관측 · 정합성커밋 이후 S3 처리 실패를 감지 가능한 구조로 전환▶
문제
afterCommit으로 옮긴 S3 이동이 실패하면 로그만 남고 끝났습니다. DB의 imageKey는 새 경로를 가리키는데 실제 파일은 그 경로에 없어, 사용자에게 깨진 이미지로 그대로 드러납니다.
원인
내부에서만 아는 조용한 실패가 아니라 사용자에게 노출되는 정합성 문제인데, 로그는 누군가 일부러 들여다보지 않으면 아무도 모릅니다. 이 구조의 진짜 약점은 재시도가 없다는 것이 아니라 실패를 능동적으로 감지할 수단이 없다는 점이라고 판단했습니다.
해결 과정
  1. 재시도보다 감지를 먼저 확보했습니다. 실패를 메트릭(s3.operation.failure)으로 노출하고, 재시도는 별도 메트릭으로 분리해 흡수된 실패와 사람이 개입해야 할 실패를 구분했습니다.
  2. 일시적 오류 흡수를 위해 짧은 재시도를 추가했습니다. 최초 1회 + 재시도 2회(100ms, 200ms), 응답 경로 안이라 상한을 300ms로 두었습니다.
  3. 최종 실패해도 예외를 전파하지 않습니다. 커밋이 끝난 뒤라 예외를 던져도 롤백되지 않고 재등록 중복만 유발합니다.
  4. 커밋 이후 실행 등록 로직을 공통 컴포넌트로 분리해, 예외를 삼키는 계층의 경계를 명확히 했습니다.
결과
일시적 오류는 재시도로 흡수되어 사용자에게 노출되지 않고, 최종 실패는 메트릭으로 사용자 문의 전에 인지할 수 있게 됐습니다. 기존 삭제 경로의 예외 전파 문제도 함께 해결했고, 6개 시나리오를 단위 테스트로 검증했습니다.
트레이드오프
자동 복구는 확보하지 못했습니다. 3회 모두 실패하면 운영자가 수동 복구해야 합니다. Outbox나 재시도 큐로 자동화할 수 있으나, 이미지 실패가 예약 흐름을 막지 않고 재시도로 대부분 흡수되므로 현재 규모에서는 감지 체계까지가 적정선이라고 판단했습니다.
Redis · 성능대기열 스케줄러의 탐색 비용 개선▶
문제
대기열 스케줄러가 활성 팝업을 찾을 때 redisTemplate.keys()로 전체 키를 탐색하고 있었습니다. 전체 서비스 응답 지연으로 이어질 수 있는 문제였습니다.
원인
KEYS는 전체 키를 순회하는 O(N) 명령인데, Redis는 단일 스레드라 실행 중 다른 모든 요청이 블로킹됩니다. 키가 늘면 정원 차감 같은 핵심 명령까지 멈출 수 있습니다.
해결 과정
  1. 활성 팝업 ID만 담는 Set 인덱스로 전체 탐색을 없애고 단일 스레드 블로킹을 해소했습니다.
  2. 빈 팝업을 즉시 삭제하면 확인과 제거 사이에 새 대기자가 누락될 수 있어, 삭제 시점을 조회 경로로 옮겼습니다(lazy deletion).
  3. 그래도 남는 창은 순회 전체를 Lua 스크립트로 원자화해 제거했습니다.
결과
스케줄러 주기당 Redis 왕복이 N+1회에서 1회로 줄었습니다. 전체 키 탐색이 사라져 조회 비용이 키 개수와 무관해졌고, 대기자 누락 경로는 수정 전 실패 / 수정 후 통과하는 회귀 테스트로 검증했습니다.
이후 과제
스크립트가 활성 팝업 수 N만큼 EXISTS를 순회하므로 블로킹 시간이 N에 비례합니다. 현재 규모에서는 무시할 수 있으나, 수천 단위로 늘면 배치 분할이 필요합니다.
정합성 · 분산 제어Redis 재구축 구간의 요청 유실 방지▶
문제
Redis 상태를 DB 기준으로 재구축하는 중에 들어온 예약이 사라졌습니다. DB 조회(남은 자리 30) → 신규 예약 DECR(29) → 재구축이 SET 30으로 덮어쓰면서 차감이 증발해 과다 판매로 이어지는데, 사용자는 성공 응답을 받아 아무도 인지하지 못합니다.
원인
재구축이 전부 블라인드 쓰기로 현재 값을 읽지 않고 덮어쓰니, DB 조회 시점과 쓰기 시점 사이의 변경이 모두 무시됩니다. 같은 패턴이 3개 도메인에 있었고, 슬롯 초기화는 도메인이 다른데도 예약 정원과 같은 key를 만졌습니다.
해결 과정
  1. 재구축 구간의 요청을 503으로 거절하는 게이트를 도입했습니다. 재구축은 수백 ms라 조용한 유실보다 명시적 거절이 낫다고 판단했습니다.
  2. 스코프를 도메인이 아닌 키 단위로 잡아 공통 컴포넌트화했습니다.
  3. setIfAbsent + TTL로 게이트 표시와 분산 상호배제를 겸했습니다.
  4. 게이트 해제와 DECR 경로를 각각 Lua로 원자화했습니다. 둘 다 check-then-act 구조라 분리하면 창이 남습니다.
결과
lost update 경로를 제거하고 다중 인스턴스의 중복 재구축을 막았습니다. 3개 도메인이 동일 컴포넌트를 사용하며, 키 단위 스코프로 도메인 경계를 넘는 충돌도 차단됩니다. 3개 시나리오를 검증했습니다.
트레이드오프
enqueue는 중간에 DB insert가 있어 원자화할 수 없습니다. 인터셉터로 창을 좁히고, 남은 창은 recover가 DB 기준으로 재구축하며 수렴시킵니다.
장애 격리단일 장애점(Redis) 대비 — CircuitBreaker 장애 격리와 복구▶
문제
Redis에 장애가 생기면 서버가 응답을 기다리며 타임아웃마다 스레드를 낭비하고 요청이 쌓일 수 있다고 예상했습니다.
원인
Redis 호출이 예약 생성 경로의 필수 단계라, 응답이 없으면 그 뒤 로직이 전부 멈춥니다. 개별 요청의 실패를 넘어 한 의존성의 장애가 서버 전체로 번지는 구조였습니다.
해결 과정
임계값은 운영 트래픽이 없는 환경이라 Sentinel 복구 시간과 일반 권장값 기준 초기값으로 두고, 운영 데이터 확보 후 재조정하는 것을 전제로 했습니다.
  1. 폴백을 경로별로 분리했습니다. 차감은 남은 자리를 모른 채 통과시키면 오버셀이라 예외로 차단하고, 복구는 DB 취소와 환불이 끝난 뒤라 null 반환으로 흐름을 유지합니다.
  2. slow-call 임계를 수백 ms로 낮춰 느려지기만 하는 장애에서도 스레드를 끊고, minimum-number-of-calls를 window(10)에 맞춰 명시했습니다.
결과
장애 시 대기 없이 즉시 폴백하며 스레드 점유로 인한 전파가 차단됩니다. 오버셀과 취소 흐름 중단을 각각 다른 전략으로 방어합니다.
Redis · 운영운영 종료일 기준 TTL로 카운터 키 생명주기 관리▶
문제
재고 카운터 키를 언제까지 유지해야 할지 정해야 했습니다. 너무 짧게 잡으면 이후 취소·환불 처리 중에 키가 사라져 더 큰 문제가 될 수 있었습니다.
원인
TTL 만료 시간을 슬롯 종료 시각 기준으로 잡으면, 운영 기간 내내 발생하는 취소·환불 시점에 이미 키가 만료돼 재고를 되돌릴 수 없게 됩니다.
해결 과정
  1. TTL을 슬롯 종료가 아닌 운영 종료일 기준으로 설정해 취소·환불 여유를 확보했습니다.
  2. 동시 만료 시 CPU 부하도 검토했으나, 예상 규모(약 7,000개 키)에선 문제없다고 판단했습니다.
결과
운영 기간 내 발생하는 취소·환불에서 재고 복구가 항상 가능해졌고, 운영 종료 후에는 키가 자동 정리되어 별도 삭제 로직 없이 메모리를 회수합니다.
정합성 · 외부 시스템트랜잭션 커밋 이후로 S3 이미지 처리를 미뤄 정합성 보장▶
문제
팝업스토어 등록·수정·삭제 시 S3 이미지를 트랜잭션 안에서 바로 처리하면, 이후 DB 작업이 실패해 롤백되어도 이미 옮기거나 지운 파일은 되돌릴 수 없습니다.
원인
DB는 롤백으로 복구되지만 S3 파일 조작은 외부 시스템이라 롤백 대상이 아닙니다. 트랜잭션 중간에 파일을 건드리면 DB 상태와 실제 파일이 어긋날 수 있습니다.
해결 과정
파일 조작을 트랜잭션이 확정된 뒤에만 일어나게 하고, 확정되지 못한 파일은 위치만으로 구분되도록 설계했습니다.
  1. 이미지 이동·삭제를 afterCommit 시점으로 미루고, 트랜잭션 없이 호출되는 경우를 대비한 fallback도 두었습니다.
  2. 업로드는 temp에, 커밋 성공 시에만 final로 이동하도록 prefix를 분리했습니다. temp 잔류 파일은 DB 대조 없이 판별되며 Lifecycle 규칙(24h)으로 자동 정리됩니다.
결과
DB 롤백 시에도 파일이 그대로 남아 DB 상태와 S3 실제 파일이 어긋나지 않게 됐고, 연결되지 않은 이미지는 별도 배치 없이 회수됩니다.
인프라 · 배포
애플리케이션을 실제로 운영 가능한 상태로 올리기 위해, 인프라를 코드로 정의하고 배포를 자동화했습니다. Terraform이 인프라를, GitHub Actions가 애플리케이션 배포를 담당하도록 경계를 나눴습니다.
IaCTerraform으로 인프라 코드화▶
문제
콘솔에서 수동으로 만든 EC2·보안그룹·IAM은 재현이 불가능했습니다. 어떤 설정을 했는지 기록이 남지 않고, 인스턴스를 다시 만들려면 같은 클릭을 반복해야 했습니다.
해결 과정
  1. EC2·보안그룹·EIP·IAM 역할·S3를 Terraform으로 정의했습니다.
  2. 개인키가 state에 평문으로 남지 않도록 키페어는 코드화 대상에서 제외했습니다.
  3. state는 S3 원격 저장소로 분리하고, 부트스트랩용 구성을 따로 두어 순환 의존을 해소했습니다.
  4. user_data로 Docker·MySQL·Redis·Nginx 초기 설치를 자동화했습니다.
결과
apply 한 번으로 동일한 인프라가 재현되고, destroy로 잔여 리소스 없이 정리됩니다. 인스턴스를 통째로 교체해도 MySQL 데이터가 별도 볼륨에 남아 유지되는 것을 확인했습니다.
검증코드 검증으로는 잡히지 않는 부팅 시점 실패 5건▶
문제
validate와 plan을 모두 통과했음에도 user_data가 부팅 중 실패했고, apply는 성공으로 끝나 실패가 드러나지 않았습니다.
원인
user_data는 EC2 내부에서 부팅 중에 실행되므로 Terraform은 그 결과를 알 수 없습니다. 게다가 set -e 때문에 첫 실패 지점에서 스크립트 전체가 중단돼 이후 설치가 하나도 진행되지 않았습니다.
해결 과정
  1. Ubuntu 24.04에서 제거된 awscli apt 패키지를 공식 설치 프로그램으로 교체했습니다.
  2. 24.04의 SSH 소켓 활성화로 부팅 시점에 존재하지 않는 /run/sshd를 사전 생성했습니다.
  3. unzip·gpg가 기존 파일을 만나면 대화형 프롬프트에서 멈추는 문제를 비대화형 옵션으로 해소했습니다.
  4. 볼륨이 연결되지 않아도 mkfs가 진행되던 경로를 명시적 실패로 바꿔 데이터 유실을 차단했습니다.
결과
클린 부팅에서 cloud-init 완주를 확인했습니다. 외부에서 애플리케이션·DB·Redis 포트가 모두 닫히고 Nginx만 노출되는 것도 함께 검증했습니다.

문제
기존 배포는 컨테이너를 내리고 다시 올리는 방식이라 전환 구간에 33초의 다운타임이 발생했습니다.
해결 과정
  1. 새 버전을 별도 포트에 먼저 띄우고, 헬스체크를 통과한 뒤에만 Nginx 업스트림을 전환하도록 했습니다.
  2. 헬스체크 실패 시 새 컨테이너만 제거하고 기존 컨테이너와 Nginx 설정은 그대로 유지합니다.
  3. 컨테이너에서 IAM 역할을 받도록 IMDS hop limit을 조정해, 배포 파이프라인에서 AWS 액세스 키를 제거했습니다.
결과
배포 중 요청이 끊기지 않는 것을 확인했습니다 — 다운타임 33초에서 0초. 실제 배포 실패 상황에서도 롤백 경로가 의도대로 동작해, 기존 서비스가 중단 없이 유지되는 것을 확인했습니다.

문제
재고 차감과 반환은 동시성 부하 상태가 다릅니다. 트래픽이 다른 상황에 같은 락 전략을 사용하면 각 상황에서 불필요한 비용이 발생하고 성능이 떨어질 수 있다고 판단했습니다.
원인
예약 오픈 시의 정원 차감은 수천~수만 명이 몰려 충돌이 극심하지만, 정원 반환(취소·수정)은 본인 예약 대상이라 충돌이 드뭅니다.

  2. 두 방식 모두 예약 통과는 1건이었으나, 성능이 분산 락 1,390 req/s · 낙관적 락 321 req/s로 분산 락이 우세했습니다.

결과

트랜잭션스케줄러 @Transactional 자기 호출 문제 해결▶
문제
재고를 방출하는 스케줄러에서 재고 반환과 예약 취소를 한 트랜잭션으로 처리해야 했는데, 실제로는 트랜잭션이 걸리지 않아 부분 실행 시 롤백되지 않는 위험이 있었습니다.
원인
스케줄러가 같은 클래스 안의 @Transactional 메서드를 직접 호출하고 있었습니다. Spring의 @Transactional은 프록시를 통해 동작하는데, 같은 클래스 내부 호출은 프록시를 거치지 않아 트랜잭션이 적용되지 않습니다.
해결 과정
  1. 트랜잭션이 필요한 로직을 별도 서비스 클래스로 분리했습니다.
  2. 다른 빈으로 분리되면 호출 시 프록시를 거치게 되어 @Transactional이 정상 동작합니다.
결과
정원 반환과 예약 취소가 하나의 트랜잭션으로 묶여, 중간 실패 시 함께 롤백되도록 원자성을 보장합니다.
어뷰징 대응취소 재고를 지연 방출해 즉시 선점 완화 (CANCEL_PENDING)▶
문제
취소 재고를 즉시 반환하면 반환 시점이 예측 가능해, 자동화된 요청이 정상 사용자보다 유리하게 자리를 잡을 수 있습니다.
원인
오픈 직후 30분 이내에 취소하거나 같은 유저가 반복 취소할 경우, 암표·어뷰징 목적의 유저가 생길 것이라고 판단했습니다.
해결 과정
  1. 어뷰징이 의심되는 취소는 CANCEL_PENDING 상태로 두어, 동적 스케줄러가 랜덤한 시간에 반환하도록 했습니다.
  2. Redis TTL은 만료 시점에 콜백을 보장하지 않아 알림 유실 가능성이 있었습니다. 재고가 영영 방출되지 않을 위험이 있어, 방출 시점을 DB에 저장하고 서버 재시작 시에도 복구 가능한 DB 기반 동적 스케줄러로 구현했습니다.
결과
완전한 어뷰징 방지는 아니지만, 반환 시점을 제어하는 것만으로 즉시 선점 난이도를 높일 수 있었습니다.
